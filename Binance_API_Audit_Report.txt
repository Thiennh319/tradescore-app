PART D — REQUEST VOLUME ESTIMATE (STEADY STATE)
──────────────────────────────────────────────────

Per 60s unified scan cycle (4 symbols, all modules active, cache cold):

  V3/V4 per symbol (fetchAllMarketData):
    - 5 kline REST calls
    - 1 depth REST
    - 1 forceOrder WebSocket session (~2s)
    - 2 OI REST (openInterest + hist)
    - 1 funding REST
    - 1 long/short REST
    = ~11 REST + 1 WS per symbol × 4 = ~44 REST + 4 WS
  Plus per symbol: ticker + 24h alt = +2 REST × 4 = +8 REST
  Plus BTC 24h once = +1 REST
  V4.1 per symbol (fetchRawMarketV41):
    - 5 kline REST (some overlap with V3/V4 cache if same interval/limit)
    - 1 direct funding REST (no shared cache)
    = ~6 REST × 4 = ~24 REST

  Whale Radar (every 5 min, 4 symbols):
    - depth + ticker + 1h klines per symbol = 3 REST × 4 = 12 REST per 5 min

  Locked plan monitor (30s, 1 symbol when active):
    - Full fetchAllMarketData + ticker ≈ 12 REST + 1 WS per 30s

  Price / pending monitors (60s, variable symbols):
    - 1 ticker REST per unique OPEN/PENDING symbol

Note: binanceApi dedup + storage cache significantly reduces actual HTTP count when
intervals overlap (e.g. ticker 3s cache, klines 60s cache, shared fetchKlines between V3 and V41 for 4h).
